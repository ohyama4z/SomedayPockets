# ADR-005: ✅ knowledge/は1知見1ファイルで管理する
<!-- ファイル名: 005-knowledge_1知見1ファイルルールを採用する.md -->

- **日付**: 2026-06-04
- **ステータス**: ✅ 承認済み
- **チケット**: #90

## コンテキスト

`knowledge/` には開発知見をファイルで書き溜めているが、1ファイルにどの粒度で知見を入れるかが明文化されていなかった。命名規則（`日付_チケット番号_連番_タイトル.md`）は定義済みだったものの、AIが1ファイルに複数のトピックをまとめてしまう事象が発生した。

複数トピックを1ファイルに混在させると、後から特定の学びを参照しづらく、ファイルが肥大化する。実際 #49 では、1ファイルに5つの知見が混在していた T28 を5ファイルに分割する是正が必要になった。

この粒度ルールを暗黙知ではなくADRとして確定させ、CLAUDE.md からも参照できるようにする。

## 検討した選択肢

### 選択肢A: 1知見1ファイル
- **pros**: 各知見が独立した参照単位になる。INDEX.mdで1行1知見のテーブル化がしやすく検索性が高い。複数チケットにまたがる学びの集約・参照も容易。1知見だけ更新・廃止する操作が局所化する
- **cons**: ファイル数が増える（ただしINDEX.mdで一覧できるため実害は小さい）

### 選択肢B: トピック別1ファイル
- **pros**: 関連する知見がまとまり、テーマ単位で見渡しやすい
- **cons**: 「トピック」の境界が曖昧で粒度がぶれる。1ファイルが肥大化し、特定の学びを参照しづらくなる（#49で是正したのと同じ問題に戻る）

### 選択肢C: 日付別1ファイル
- **pros**: 作業ログとしては時系列で追いやすい
- **cons**: 1日の作業に複数トピックが混在する。フロー情報（作業ログ）寄りになり、ストック情報としての再利用性が低い

## 決定

**選択肢Aを採用する。** `knowledge/` は1ファイルにつき1つの知見（1トピック）で管理する。

### 付随ルール

**粒度の目安:**
- 1ファイル = 独立して参照・検索できる1つの学び。複数の学びがあれば連番を分けて別ファイルにする

**命名規則:** `日付_チケット番号_連番_タイトル.md`（例: `2026-03-14_T28_1_SKILL.mdフロントマターの仕様.md`）
- タイトルはその知見を一言で表す具体的な名前にする（例: `Stopフックによる定期プロンプト`）
- 抽象的・包括的な名前は避ける（悪い例: `ClaudeCodeの仕様`、`開発の学び`）

**フォーマット:**
```markdown
# タイトル

- **日付**: YYYY-MM-DD
- **チケット**: #番号
- **作業**: 作業内容の簡潔な説明

## 知見

（1つのトピックに絞って簡潔に記述）
```

**INDEX.md:** 各ファイルを1行1エントリでテーブル化し、サマリーに知見の核心を1行で記す。

### 理由

各知見が独立した参照単位になるため、INDEX.mdでのテーブル化・検索がしやすく、複数チケットにまたがる学びの集約も容易になる。トピック別（B）・日付別（C）はいずれも1ファイルに複数トピックが混在しやすく、#49 で是正した肥大化・参照困難の問題に逆戻りする。ファイル数が増えるデメリットはINDEX.mdで吸収できる。
